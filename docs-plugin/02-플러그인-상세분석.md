## 1. commit-commands 분석

### 디렉토리 구조
```
plugins/commit-commands/
├── .claude-plugin/
│   └── plugin.json          # 플러그인 메타데이터
├── commands/
│   ├── commit.md           # /commit 명령어
│   ├── commit-push-pr.md   # /commit-push-pr 명령어
│   └── clean_gone.md       # /clean_gone 명령어
└── README.md
```

### plugin.json 분석
```json
{
  "name": "commit-commands",
  "description": "Streamline your git workflow with simple commands for committing, pushing, and creating pull requests",
  "version": "1.0.0",
  "author": {
    "name": "Anthropic",
    "email": "support@anthropic.com"
  }
}
```

### /commit 명령어 분석

**파일**: `commands/commit.md`

#### Frontmatter 설정
```yaml
---
allowed-tools: Bash(git add:*), Bash(git status:*), Bash(git commit:*)
description: Create a git commit
---
```

**주요 포인트**:
- `allowed-tools`: 허용된 도구를 제한하여 명령어가 git 관련 작업만 수행하도록 함
- 각 도구는 `ToolName(pattern)` 형식으로 지정
- `*`는 와일드카드로 모든 하위 명령어 허용

#### 명령어 동작 방식

1. **Context 제공**:
   - `!`git status`` - 현재 git 상태
   - `!`git diff HEAD`` - staged/unstaged 변경사항
   - `!`git branch --show-current`` - 현재 브랜치
   - `!`git log --oneline -10`` - 최근 커밋 10개

   > **동적 명령어 실행**: `!`명령어`` 구문은 실행 시점에 명령어를 실행하고 결과를 컨텍스트에 포함

2. **Task 정의**:
   ```markdown
   Based on the above changes, create a single git commit.

   You have the capability to call multiple tools in a single response.
   Stage and create the commit using a single message.
   Do not use any other tools or do anything else.
   ```

#### 핵심 학습 포인트
- 명령어 파일은 **프롬프트 템플릿**임
- `allowed-tools`로 명령어 범위를 제한하여 안전성 확보
- 동적 컨텍스트(`!`...``)를 통해 최신 정보 제공
- 명확한 지시사항으로 AI 동작 제어

## 2. feature-dev 분석

### 디렉토리 구조
```
plugins/feature-dev/
├── .claude-plugin/
│   └── plugin.json
├── commands/
│   └── feature-dev.md      # 7단계 워크플로우
├── agents/
│   ├── code-explorer.md    # 코드베이스 탐색
│   ├── code-architect.md   # 아키텍처 설계
│   └── code-reviewer.md    # 코드 리뷰
└── README.md
```

### /feature-dev 명령어 분석

**파일**: `commands/feature-dev.md`

#### 7단계 워크플로우 구조

```
Phase 1: Discovery         → 요구사항 이해
Phase 2: Exploration       → 코드베이스 탐색 (2-3 agents 병렬)
Phase 3: Questions         → 모호한 부분 명확화
Phase 4: Design           → 아키텍처 설계 (2-3 agents 병렬)
Phase 5: Implementation   → 기능 구현
Phase 6: Review           → 품질 검토 (3 agents 병렬)
Phase 7: Summary          → 완료 요약
```

#### Phase 2: Codebase Exploration 분석

```markdown
**Actions**:
1. Launch 2-3 code-explorer agents in parallel. Each agent should:
   - Trace through the code comprehensively
   - Target a different aspect of the codebase
   - Include a list of 5-10 key files to read

**Example agent prompts**:
- "Find features similar to [feature] and trace through their implementation comprehensively"
- "Map the architecture and abstractions for [feature area]"
```

**핵심 전략**:
- **병렬 에이전트 실행**: 여러 관점에서 동시에 분석
- **파일 목록 반환**: 에이전트가 중요 파일 목록을 반환하도록 요청
- **실제 파일 읽기**: 에이전트 완료 후 반환된 파일들을 모두 읽음

#### Phase 3: Clarifying Questions (중요!)

```markdown
**CRITICAL**: This is one of the most important phases. DO NOT SKIP.

**Actions**:
1. Review the codebase findings and original feature request
2. Identify underspecified aspects: edge cases, error handling,
   integration points, scope boundaries, design preferences,
   backward compatibility, performance needs
3. **Present all questions to the user in a clear, organized list**
4. **Wait for answers before proceeding to architecture design**
```

**왜 중요한가**:
- 구현 전 모호성 제거
- 잘못된 가정으로 인한 재작업 방지
- 사용자 요구사항 명확화

#### Phase 4: Architecture Design

```markdown
1. Launch 2-3 code-architect agents in parallel with different focuses:
   - minimal changes (smallest change, maximum reuse)
   - clean architecture (maintainability, elegant abstractions)
   - pragmatic balance (speed + quality)
2. Review all approaches and form your opinion
3. Present to user: summary, trade-offs, **your recommendation**
4. **Ask user which approach they prefer**
```

**설계 접근법**:
- **다양한 관점**: 최소 변경 vs 깔끔한 설계 vs 균형
- **트레이드오프 명시**: 각 접근법의 장단점
- **AI 추천 제공**: 단순히 선택지만 주는 것이 아니라 추천과 이유 제공

### code-explorer 에이전트 분석

**파일**: `agents/code-explorer.md`

#### Frontmatter 설정
```yaml
---
name: code-explorer
description: Deeply analyzes existing codebase features by tracing execution paths
tools: Glob, Grep, LS, Read, NotebookRead, WebFetch, TodoWrite, WebSearch, KillShell, BashOutput
model: sonnet
color: yellow
---
```

**설정 항목**:
- `name`: 에이전트 식별자
- `description`: 에이전트 설명
- `tools`: 사용 가능한 도구 목록
- `model`: 사용할 AI 모델 (sonnet/opus/haiku)
- `color`: UI에서 표시할 색상

#### 분석 방법론

**1. Feature Discovery**
```markdown
- Find entry points (APIs, UI components, CLI commands)
- Locate core implementation files
- Map feature boundaries and configuration
```

**2. Code Flow Tracing**
```markdown
- Follow call chains from entry to output
- Trace data transformations at each step
- Identify all dependencies and integrations
- Document state changes and side effects
```

**3. Architecture Analysis**
```markdown
- Map abstraction layers (presentation → business logic → data)
- Identify design patterns and architectural decisions
- Document interfaces between components
- Note cross-cutting concerns (auth, logging, caching)
```

**4. Implementation Details**
```markdown
- Key algorithms and data structures
- Error handling and edge cases
- Performance considerations
- Technical debt or improvement areas
```

#### 출력 형식

```markdown
Provide a comprehensive analysis that helps developers understand
the feature deeply enough to modify or extend it. Include:

- Entry points with file:line references
- Step-by-step execution flow with data transformations
- Key components and their responsibilities
- Architecture insights: patterns, layers, design decisions
- Dependencies (external and internal)
- Observations about strengths, issues, or opportunities
- List of files that you think are absolutely essential
```

**중요**: 파일 경로와 라인 번호를 항상 포함!

## 3. pr-review-toolkit 분석

### 6가지 전문 에이전트

#### 1. comment-analyzer
- **목적**: 주석과 문서의 정확성 검토
- **검토 항목**:
  - 주석이 코드와 일치하는가?
  - 문서가 충분한가?
  - 오해의 소지가 있는 주석은 없는가?

#### 2. pr-test-analyzer
- **목적**: 테스트 커버리지 분석
- **검토 항목**:
  - 새 기능에 테스트가 있는가?
  - 엣지 케이스를 테스트하는가?
  - 테스트가 의미 있는가?

#### 3. silent-failure-hunter
- **목적**: 조용한 실패 패턴 감지
- **검토 항목**:
  - 에러가 무시되는가?
  - try-catch가 빈 블록인가?
  - 실패해도 계속 진행하는가?

#### 4. type-design-analyzer
- **목적**: 타입 설계 검토
- **검토 항목**:
  - 타입이 안전한가?
  - 불변식이 유지되는가?
  - any/unknown의 남용은 없는가?

#### 5. code-reviewer
- **목적**: 일반 코드 품질 검토
- **검토 항목**:
  - CLAUDE.md 규칙 준수
  - 버그 감지
  - 코드 스타일

#### 6. code-simplifier
- **목적**: 코드 단순화 제안
- **검토 항목**:
  - 복잡도 감소 가능성
  - 중복 코드 제거
  - 가독성 개선

### 에이전트 특화 전략

**핵심 아이디어**: 하나의 범용 에이전트보다 여러 전문 에이전트가 더 효과적

**장점**:
- 각 에이전트가 특정 문제에 집중
- 병렬 실행으로 빠른 검토
- 전문화된 프롬프트로 높은 품질

## 4. security-guidance 분석

### PreToolUse Hook 구조

**파일**: `hooks/hooks.json`

```json
{
  "description": "Security reminder hook that warns about potential security issues when editing files",
  "hooks": {
    "PreToolUse": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python3 ${CLAUDE_PLUGIN_ROOT}/hooks/security_reminder_hook.py"
          }
        ],
        "matcher": "Edit|Write|MultiEdit"
      }
    ]
  }
}
```

**구조 분석**:
- `hooks.PreToolUse`: 도구 사용 전에 실행
- `matcher`: 어떤 도구에 적용할지 정규표현식으로 지정
- `command`: 실행할 스크립트
- `${CLAUDE_PLUGIN_ROOT}`: 플러그인 루트 디렉토리 환경변수

### 보안 패턴 감지 로직

**파일**: `hooks/security_reminder_hook.py`

#### 패턴 정의 구조

```python
SECURITY_PATTERNS = [
    {
        "ruleName": "github_actions_workflow",
        "path_check": lambda path: ".github/workflows/" in path and path.endswith((".yml", ".yaml")),
        "reminder": "경고 메시지..."
    },
    {
        "ruleName": "child_process_exec",
        "substrings": ["child_process.exec", "exec(", "execSync("],
        "reminder": "경고 메시지..."
    }
]
```

**두 가지 매칭 방식**:
1. **path_check**: 파일 경로 기반 체크
2. **substrings**: 파일 내용에서 문자열 검색

#### 상태 관리

```python
def get_state_file(session_id):
    return os.path.expanduser(f"~/.claude/security_warnings_state_{session_id}.json")

def load_state(session_id):
    # 세션별로 이미 표시한 경고 로드

def save_state(session_id, shown_warnings):
    # 표시한 경고 저장
```

**중요 포인트**:
- 세션별 상태 관리 (같은 경고를 반복 표시하지 않음)
- 30일 후 자동 정리
- 파일 경로 + 룰 이름으로 고유 키 생성

#### Hook 종료 코드

```python
sys.exit(0)  # 도구 실행 허용
sys.exit(2)  # 도구 실행 차단 (경고 표시)
```

**PreToolUse Hook의 특별한 점**:
- `exit(0)`: 도구가 정상 실행됨
- `exit(2)`: 도구 실행이 차단됨 (사용자가 확인 필요)

### 감지하는 보안 패턴

1. **GitHub Actions Workflow**
   - Command Injection 취약점
   - 안전한 환경변수 사용법 제시

2. **child_process.exec**
   - Shell Injection 위험
   - `execFileNoThrow` 대안 제시

3. **eval / new Function**
   - Code Injection

4. **dangerouslySetInnerHTML / innerHTML**
   - XSS 취약점

5. **pickle (Python)**
   - Deserialization 공격

6. **os.system (Python)**
   - Command Injection

## 5. learning-output-style 분석

### SessionStart Hook

**파일**: `hooks/hooks.json`

```json
{
  "description": "Learning mode hook that adds interactive learning instructions",
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PLUGIN_ROOT}/hooks-handlers/session-start.sh"
          }
        ]
      }
    ]
  }
}
```

**SessionStart Hook의 특징**:
- 세션 시작 시 한 번만 실행
- AI의 시스템 프롬프트에 추가 컨텍스트 주입
- 사용자 경험을 변경

### Hook 출력 형식

**파일**: `hooks-handlers/session-start.sh`

```bash
cat << 'EOF'
{
  "hookSpecificOutput": {
    "hookEventName": "SessionStart",
    "additionalContext": "추가 컨텍스트..."
  }
}
EOF
```

**JSON 출력 구조**:
- `hookEventName`: 어떤 Hook인지 명시
- `additionalContext`: AI에게 추가로 제공할 지시사항

### Learning Mode 철학

```markdown
Instead of implementing everything yourself, identify opportunities
where the user can write 5-10 lines of meaningful code that shapes the solution.

Focus on business logic, design choices, and implementation strategies
where their input truly matters.
```

#### 사용자 기여 요청 시점

**요청해야 할 때**:
- Business logic with multiple valid approaches
- Error handling strategies
- Algorithm implementation choices
- Data structure decisions
- User experience decisions
- Design patterns and architecture choices

**요청하지 말아야 할 때**:
- Boilerplate or repetitive code
- Obvious implementations with no meaningful choices
- Configuration or setup code
- Simple CRUD operations

#### 요청 패턴

```markdown
Before requesting code:
1. Create the file with surrounding context
2. Add function signature with clear parameters/return type
3. Include comments explaining the purpose
4. Mark the location with TODO or clear placeholder

When requesting:
- Explain what you've built and WHY this decision matters
- Reference the exact file and prepared location
- Describe trade-offs to consider, constraints, or approaches
- Frame it as valuable input that shapes the feature
- Keep requests focused (5-10 lines of code)
```

**예시 요청**:

```
Context: I've set up the authentication middleware.
The session timeout behavior is a security vs. UX trade-off.

Request: In auth/middleware.ts, implement the handleSessionTimeout()
function to define the timeout behavior.

Guidance: Consider: auto-extending improves UX but may leave
sessions open longer; hard timeouts are more secure but
might frustrate active users.
```

### Explanatory Mode 통합

Learning Mode는 Explanatory Mode도 포함:

```markdown
★ Insight ─────────────────────────────────────
[2-3 key educational points]
─────────────────────────────────────────────────
```

**특징**:
- 코드 작성 전후에 간략한 교육적 설명
- 코드베이스 특화된 인사이트
- 일반적인 프로그래밍 개념이 아닌 특정 코드 설명

## 핵심 학습 요약

### Commands 플러그인 작성 시

1. **Frontmatter로 범위 제한**
   - `allowed-tools`로 도구 제한
   - `description`으로 명령어 설명

2. **동적 컨텍스트 활용**
   - `!`명령어``로 최신 정보 제공
   - git, 파일 시스템 등 실시간 데이터

3. **명확한 지시사항**
   - AI가 정확히 무엇을 해야 하는지 명시
   - 제약사항과 요구사항 명확히

### Agents 플러그인 작성 시

1. **전문화**
   - 각 에이전트는 하나의 작업에 집중
   - 범용 에이전트보다 전문 에이전트가 효과적

2. **도구 선택**
   - 에이전트가 필요한 도구만 제공
   - 불필요한 도구는 제외

3. **출력 형식 명시**
   - 에이전트가 반환해야 할 정보 구체화
   - 파일 경로, 라인 번호 등 구체적 정보 요구

### Hooks 플러그인 작성 시

1. **적절한 Hook 선택**
   - `SessionStart`: 세션 시작 시 한 번
   - `PreToolUse`: 도구 사용 전마다
   - `PostToolUse`: 도구 사용 후마다

2. **종료 코드 활용**
   - `exit(0)`: 정상 진행
   - `exit(2)`: 실행 차단 (PreToolUse)

3. **상태 관리**
   - 세션별 상태 저장
   - 반복 경고 방지
   - 정리 로직 포함
