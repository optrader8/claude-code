## 플러그인 제작 기본

### 플러그인의 기본 구조

모든 플러그인은 최소한 다음 구조를 가져야 합니다:

```
my-plugin/
├── .claude-plugin/
│   └── plugin.json      # 필수: 플러그인 메타데이터
└── README.md            # 권장: 플러그인 설명
```

### plugin.json 필수 필드

```json
{
  "name": "my-plugin",
  "description": "플러그인 설명",
  "version": "1.0.0",
  "author": {
    "name": "Your Name",
    "email": "your.email@example.com"
  }
}
```

### 플러그인 타입별 추가 구조

```
my-plugin/
├── .claude-plugin/
│   └── plugin.json
├── commands/            # Commands 플러그인
│   └── *.md
├── agents/              # Agents 플러그인
│   └── *.md
├── hooks/               # Hooks 플러그인
│   └── hooks.json
├── hooks-handlers/      # Hook 스크립트
│   └── *.sh, *.py
└── README.md
```

## Commands 플러그인 만들기

Commands 플러그인은 `/명령어` 형식으로 사용자가 호출할 수 있는 슬래시 명령어를 제공합니다.

### 예제 1: 간단한 TODO 명령어 만들기

#### 1단계: 플러그인 디렉토리 생성

```bash
mkdir -p my-todo-plugin/.claude-plugin
mkdir -p my-todo-plugin/commands
```

#### 2단계: plugin.json 작성

```json
{
  "name": "todo-commands",
  "description": "TODO 관리 명령어",
  "version": "1.0.0",
  "author": {
    "name": "Your Name",
    "email": "your@email.com"
  }
}
```

#### 3단계: 명령어 파일 작성

**파일**: `commands/add-todo.md`

```markdown
---
description: Add a new TODO item
argument-hint: TODO description
---

## Your task

Add the following TODO item to the TODO.md file in the project root:

- [ ] $ARGUMENTS

If the TODO.md file doesn't exist, create it with a "# TODO" header first.

After adding the item, confirm the addition to the user.
```

**Frontmatter 설명**:
- `description`: 명령어 설명 (필수)
- `argument-hint`: 인자 힌트 (선택)
- `allowed-tools`: 허용된 도구 제한 (선택)

**$ARGUMENTS 변수**:
- 사용자가 입력한 인자가 자동으로 치환됨
- 예: `/add-todo Buy milk` → `$ARGUMENTS = "Buy milk"`

#### 4단계: 테스트

명령어를 실행해봅니다:
```
/add-todo 우유 사기
```

### 예제 2: Git 통계 명령어 (도구 제한)

**파일**: `commands/git-stats.md`

```markdown
---
allowed-tools: Bash(git log:*), Bash(git shortlog:*)
description: Show git repository statistics
---

## Context

- Repository name: !`basename $(git rev-parse --show-toplevel)`
- Current branch: !`git branch --show-current`
- Total commits: !`git rev-list --count HEAD`

## Your task

Analyze the git repository and provide statistics:

1. Top 5 contributors by commit count
2. Commit activity by day of week
3. Most active files (top 10)

Use the allowed git commands to gather this information.
Present the results in a clear, formatted manner.
```

**핵심 기법**:
- `allowed-tools`로 git 명령어만 허용
- `!`명령어``로 동적 컨텍스트 제공
- 명확한 출력 형식 요구

### 예제 3: 대화형 명령어

**파일**: `commands/create-component.md`

```markdown
---
description: Create a new React component interactively
---

## Your task

Help the user create a new React component through an interactive process:

1. **Ask for component details**:
   - Component name (PascalCase)
   - Component type (functional/class)
   - Props needed (if any)
   - Should it include TypeScript types?
   - Should it include tests?

2. **Create the component file**:
   - Use the project's existing component structure
   - Follow the project's naming conventions
   - Include proper imports

3. **Create supporting files if requested**:
   - TypeScript type definitions
   - Test file
   - Storybook story (if Storybook exists)

4. **Confirm creation**:
   - Show the file paths created
   - Suggest next steps

Ask questions one at a time and wait for user responses.
```

**대화형 명령어 패턴**:
- 단계별로 질문
- 사용자 응답 대기
- 컨텍스트를 누적하며 진행

## Agents 플러그인 만들기

Agents는 특정 작업을 전문적으로 수행하는 독립적인 AI 에이전트입니다.

### 예제 1: 성능 분석 에이전트

#### 1단계: 플러그인 디렉토리 생성

```bash
mkdir -p performance-analyzer/.claude-plugin
mkdir -p performance-analyzer/agents
```

#### 2단계: plugin.json 작성

```json
{
  "name": "performance-analyzer",
  "description": "코드 성능 분석 에이전트",
  "version": "1.0.0",
  "author": {
    "name": "Your Name",
    "email": "your@email.com"
  }
}
```

#### 3단계: 에이전트 파일 작성

**파일**: `agents/perf-analyzer.md`

```markdown
---
name: perf-analyzer
description: Analyzes code for performance bottlenecks and suggests optimizations
tools: Glob, Grep, Read, WebSearch
model: sonnet
color: red
---

You are an expert performance analyst specializing in identifying
bottlenecks and optimization opportunities.

## Your Mission

Analyze the codebase for performance issues and provide actionable recommendations.

## Analysis Areas

### 1. Algorithm Complexity
- Identify O(n²) or worse algorithms
- Suggest more efficient alternatives
- Look for unnecessary nested loops

### 2. Memory Usage
- Find memory leaks
- Identify excessive object creation
- Suggest caching opportunities

### 3. I/O Operations
- Identify blocking I/O
- Suggest async/await improvements
- Look for unnecessary file system operations

### 4. Database Queries
- Find N+1 query problems
- Suggest query optimization
- Look for missing indexes

### 5. Bundle Size (Frontend)
- Identify large dependencies
- Suggest code splitting opportunities
- Find unused imports

## Output Format

Provide your analysis in this format:

### Performance Issues Found

For each issue:
1. **Location**: file:line
2. **Issue**: Brief description
3. **Impact**: High/Medium/Low
4. **Current Code**: Show problematic code
5. **Suggested Fix**: Show improved code
6. **Explanation**: Why this is better
7. **Estimated Improvement**: Performance gain estimate

### Summary

- Total issues found: X
- High priority: X
- Medium priority: X
- Low priority: X

### Recommended Priorities

List the top 3-5 issues to fix first, with reasoning.
```

**에이전트 Frontmatter 설명**:
- `name`: 에이전트 식별자 (필수)
- `description`: 에이전트 설명 (필수)
- `tools`: 사용 가능한 도구 목록 (필수)
- `model`: AI 모델 선택 (선택, 기본값: sonnet)
  - `opus`: 가장 강력, 느림, 비쌈
  - `sonnet`: 균형잡힌 선택 (기본값)
  - `haiku`: 빠르고 저렴, 간단한 작업용
- `color`: UI 색상 (선택)

### 예제 2: 문서 생성 에이전트

**파일**: `agents/doc-generator.md`

```markdown
---
name: doc-generator
description: Generates comprehensive documentation for code files
tools: Glob, Grep, Read, Write
model: sonnet
color: blue
---

You are a documentation specialist who creates clear, comprehensive documentation.

## Your Mission

Generate high-quality documentation for the specified code files or modules.

## Documentation Standards

### For Functions/Methods
```markdown
/**
 * Brief description of what the function does
 *
 * @param paramName - Description of parameter
 * @returns Description of return value
 * @throws Description of possible errors
 *
 * @example
 * ```typescript
 * // Usage example
 * const result = myFunction(arg1, arg2);
 * ```
 */
```

### For Classes
```markdown
/**
 * Brief description of the class purpose
 *
 * @remarks
 * Detailed explanation of the class design and usage patterns
 *
 * @example
 * ```typescript
 * // Usage example
 * const instance = new MyClass(options);
 * instance.doSomething();
 * ```
 */
```

### For Modules/Files
Create a README.md with:
1. **Overview**: What this module does
2. **Installation**: How to use it
3. **API Reference**: List of exported functions/classes
4. **Examples**: Common usage patterns
5. **Architecture**: How it works internally (if complex)

## Process

1. **Read the code thoroughly**
2. **Understand the purpose and design**
3. **Identify public APIs**
4. **Generate documentation**:
   - Inline comments for complex logic
   - JSDoc/docstrings for functions/classes
   - README for modules
5. **Include examples**
6. **Verify accuracy**

## Output

Present the generated documentation and ask the user if they want
you to write it to the files or just review it first.
```

### 에이전트 호출 방법

Commands에서 에이전트를 호출할 수 있습니다:

**파일**: `commands/analyze-performance.md`

```markdown
---
description: Analyze code performance and suggest optimizations
---

## Your task

Launch the perf-analyzer agent to analyze the codebase for performance issues.

After the agent completes:
1. Review the findings
2. Summarize the top 3 issues
3. Ask the user which issues they want to fix
```

## Hooks 플러그인 만들기

Hooks는 특정 이벤트 발생 시 자동으로 실행되는 스크립트입니다.

### Hook 타입

1. **SessionStart**: 세션 시작 시 한 번 실행
2. **PreToolUse**: 도구 사용 전 실행
3. **PostToolUse**: 도구 사용 후 실행

### 예제 1: 코드 포맷 체크 (PreToolUse Hook)

#### 1단계: 플러그인 디렉토리 생성

```bash
mkdir -p format-checker/.claude-plugin
mkdir -p format-checker/hooks
mkdir -p format-checker/hooks-handlers
```

#### 2단계: plugin.json 작성

```json
{
  "name": "format-checker",
  "description": "코드 포맷 체크 Hook",
  "version": "1.0.0",
  "author": {
    "name": "Your Name",
    "email": "your@email.com"
  }
}
```

#### 3단계: hooks.json 작성

**파일**: `hooks/hooks.json`

```json
{
  "description": "Format checker hook that warns about unformatted code",
  "hooks": {
    "PreToolUse": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PLUGIN_ROOT}/hooks-handlers/check-format.sh"
          }
        ],
        "matcher": "Write|Edit"
      }
    ]
  }
}
```

**hooks.json 구조**:
- `description`: Hook 설명
- `hooks.PreToolUse`: PreToolUse Hook 정의
- `hooks`: 실행할 Hook 목록
  - `type`: "command" (명령어 실행)
  - `command`: 실행할 스크립트 경로
- `matcher`: 어떤 도구에 적용할지 (정규표현식)

#### 4단계: Hook 스크립트 작성

**파일**: `hooks-handlers/check-format.sh`

```bash
#!/bin/bash

# Read hook input from stdin
INPUT=$(cat)

# Parse JSON to get tool name and file path
TOOL_NAME=$(echo "$INPUT" | jq -r '.tool_name')
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')

# Only check JS/TS files
if [[ ! "$FILE_PATH" =~ \.(js|ts|jsx|tsx)$ ]]; then
  exit 0  # Allow - not a JS/TS file
fi

# Check if prettier is configured
if [ ! -f ".prettierrc" ] && [ ! -f ".prettierrc.json" ] && [ ! -f "prettier.config.js" ]; then
  exit 0  # Allow - no prettier config
fi

# Get the new content
NEW_CONTENT=$(echo "$INPUT" | jq -r '.tool_input.new_string // .tool_input.content // empty')

if [ -z "$NEW_CONTENT" ]; then
  exit 0  # Allow - no content to check
fi

# Check format using prettier
FORMATTED=$(echo "$NEW_CONTENT" | npx prettier --parser typescript 2>/dev/null)

if [ "$NEW_CONTENT" != "$FORMATTED" ]; then
  echo "⚠️  Warning: The code is not formatted according to Prettier rules." >&2
  echo "" >&2
  echo "Please run: npx prettier --write $FILE_PATH" >&2
  echo "" >&2
  echo "Or allow me to format it automatically." >&2
  # Exit with 2 to BLOCK execution
  exit 2
fi

# Exit with 0 to ALLOW execution
exit 0
```

**중요 포인트**:
- Hook 입력은 stdin으로 JSON 형태로 제공됨
- `jq`로 JSON 파싱
- `exit 0`: 도구 실행 허용
- `exit 2`: 도구 실행 차단 (PreToolUse에서만)
- 경고는 stderr로 출력

#### Hook 입력 JSON 구조

```json
{
  "session_id": "abc123",
  "tool_name": "Write",
  "tool_input": {
    "file_path": "/path/to/file.ts",
    "content": "file content..."
  }
}
```

### 예제 2: 작업 시간 추적 (SessionStart Hook)

**파일**: `hooks/hooks.json`

```json
{
  "description": "Work time tracker",
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PLUGIN_ROOT}/hooks-handlers/track-time.sh"
          }
        ]
      }
    ]
  }
}
```

**파일**: `hooks-handlers/track-time.sh`

```bash
#!/bin/bash

# SessionStart Hook은 AI에게 추가 컨텍스트를 제공할 수 있음

cat << 'EOF'
{
  "hookSpecificOutput": {
    "hookEventName": "SessionStart",
    "additionalContext": "You are in time tracking mode.\n\nAt the end of each task, create a brief summary of:\n1. What was accomplished\n2. Time estimate for the task\n3. Any blockers encountered\n\nKeep summaries concise and in a consistent format."
  }
}
EOF

exit 0
```

**SessionStart Hook 특징**:
- `hookSpecificOutput.additionalContext`를 통해 AI 프롬프트에 컨텍스트 추가
- 세션 동안 AI의 행동을 변경할 수 있음

### 예제 3: 테스트 자동 실행 (PostToolUse Hook)

**파일**: `hooks/hooks.json`

```json
{
  "description": "Auto test runner",
  "hooks": {
    "PostToolUse": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PLUGIN_ROOT}/hooks-handlers/run-tests.py"
          }
        ],
        "matcher": "Write|Edit"
      }
    ]
  }
}
```

**파일**: `hooks-handlers/run-tests.py`

```python
#!/usr/bin/env python3

import json
import os
import subprocess
import sys

def main():
    # Read input
    input_data = json.loads(sys.stdin.read())

    file_path = input_data.get("tool_input", {}).get("file_path", "")

    # Only run tests for source files (not test files)
    if not file_path or file_path.endswith(".test.ts") or file_path.endswith(".spec.ts"):
        sys.exit(0)

    # Check if tests exist for this file
    test_file = file_path.replace(".ts", ".test.ts")
    if not os.path.exists(test_file):
        sys.exit(0)

    # Run tests
    try:
        result = subprocess.run(
            ["npm", "test", "--", test_file],
            capture_output=True,
            text=True,
            timeout=30
        )

        if result.returncode != 0:
            print(f"⚠️  Tests failed for {test_file}", file=sys.stderr)
            print(result.stdout, file=sys.stderr)
            print(result.stderr, file=sys.stderr)
    except subprocess.TimeoutExpired:
        print(f"⚠️  Tests timed out for {test_file}", file=sys.stderr)
    except Exception as e:
        print(f"⚠️  Error running tests: {e}", file=sys.stderr)

    # PostToolUse hooks don't block, just inform
    sys.exit(0)

if __name__ == "__main__":
    main()
```

**PostToolUse Hook 특징**:
- 도구 실행 후에 실행됨
- 실행을 차단할 수 없음 (정보 제공용)
- 테스트, 린팅, 알림 등에 유용

## 복합형 플러그인 만들기

Commands, Agents, Hooks를 모두 포함하는 통합 플러그인을 만들어봅시다.

### 예제: 테스트 주도 개발 (TDD) 플러그인

#### 디렉토리 구조

```
tdd-workflow/
├── .claude-plugin/
│   └── plugin.json
├── commands/
│   ├── tdd-start.md         # TDD 시작
│   └── tdd-next.md          # 다음 테스트
├── agents/
│   ├── test-writer.md       # 테스트 작성
│   └── refactor-guide.md    # 리팩토링 가이드
├── hooks/
│   └── hooks.json
├── hooks-handlers/
│   └── test-reminder.sh     # 테스트 리마인더
└── README.md
```

#### plugin.json

```json
{
  "name": "tdd-workflow",
  "description": "Test-Driven Development workflow with commands, agents, and hooks",
  "version": "1.0.0",
  "author": {
    "name": "Your Name",
    "email": "your@email.com"
  }
}
```

#### commands/tdd-start.md

```markdown
---
description: Start a new TDD workflow
argument-hint: Feature description
---

## TDD Red-Green-Refactor Workflow

You are helping the user follow Test-Driven Development.

### Your task

Guide the user through the TDD cycle for: $ARGUMENTS

## Phase 1: Red (Write a failing test)

1. Launch the test-writer agent with the feature description
2. After the agent returns, present the test to the user
3. Ask for confirmation or modifications
4. Write the test file
5. Run the test to confirm it fails
6. Show the failure message

Wait for user to proceed to Green phase.

## Phase 2: Green (Make it pass)

1. Implement the minimum code to make the test pass
2. Run the test to confirm it passes
3. Show the success message

Wait for user to proceed to Refactor phase.

## Phase 3: Refactor (Improve the code)

1. Launch the refactor-guide agent with the implemented code
2. Present refactoring suggestions
3. Ask user which improvements to apply
4. Apply the refactorings
5. Run tests to ensure they still pass

Ask if the user wants to add more tests or finish.
```

#### agents/test-writer.md

```markdown
---
name: test-writer
description: Writes comprehensive unit tests following TDD principles
tools: Glob, Grep, Read
model: sonnet
color: green
---

You are a TDD expert who writes clear, comprehensive tests.

## Your Mission

Write a failing test for the requested feature that:
1. Clearly describes the expected behavior
2. Uses the project's testing framework
3. Follows the project's test conventions
4. Covers edge cases
5. Is easy to understand

## Test Structure

### Arrange
Set up test data and dependencies

### Act
Execute the code under test

### Assert
Verify the expected behavior

## Output

Provide:
1. The complete test file content
2. Explanation of what the test verifies
3. List of edge cases covered
4. Suggestions for additional tests

Make sure the test will FAIL initially (red phase).
```

#### agents/refactor-guide.md

```markdown
---
name: refactor-guide
description: Suggests refactoring improvements while maintaining test coverage
tools: Read, Grep
model: sonnet
color: blue
---

You are a refactoring expert who improves code quality while keeping tests green.

## Your Mission

Analyze the code and suggest refactoring improvements:

### Code Smells to Look For
- Long methods
- Duplicate code
- Large classes
- Long parameter lists
- Divergent change
- Shotgun surgery

### Refactoring Patterns
- Extract method
- Extract class
- Introduce parameter object
- Replace conditional with polymorphism
- Move method

## Output Format

For each suggestion:

### 1. Issue
What code smell or problem exists

### 2. Current Code
Show the problematic code

### 3. Refactored Code
Show the improved version

### 4. Benefits
Why this is better

### 5. Risk Level
Low/Medium/High - how risky is this change?

Prioritize suggestions by impact and safety.
```

## 베스트 프랙티스

### 1. Commands 작성 시

#### ✅ 좋은 예

```markdown
---
allowed-tools: Bash(git:*), Read, Write
description: Create a feature branch with conventional naming
argument-hint: feature name
---

## Context
- Current branch: !`git branch --show-current`
- Existing branches: !`git branch -a | head -20`

## Your task
Create a new feature branch named: feature/$ARGUMENTS

1. Check if the branch already exists
2. If not, create from current branch
3. Switch to the new branch
4. Confirm to the user
```

**좋은 점**:
- 도구 제한으로 안전성 확보
- 동적 컨텍스트로 최신 정보 제공
- 명확한 단계별 지시
- 에러 처리 고려

#### ❌ 나쁜 예

```markdown
---
description: Do git stuff
---

Do whatever git operations the user wants.
```

**문제점**:
- 너무 모호함
- 도구 제한 없음
- 컨텍스트 없음
- 명확한 지시사항 없음

### 2. Agents 작성 시

#### ✅ 좋은 예

```markdown
---
name: sql-optimizer
description: Analyzes SQL queries and suggests performance optimizations
tools: Glob, Grep, Read, WebSearch
model: sonnet
color: yellow
---

You are a database performance expert.

## Your Mission
Analyze SQL queries for performance issues and suggest optimizations.

## Analysis Areas
1. Query structure and joins
2. Index usage
3. N+1 query problems
4. Subquery optimization

## Output Format
For each query:
- **Location**: file:line
- **Issue**: What's wrong
- **Optimized Query**: Improved version
- **Explanation**: Why it's better
- **Expected Improvement**: Estimated performance gain

Include specific file paths and line numbers.
```

**좋은 점**:
- 전문화된 목적
- 필요한 도구만 제공
- 명확한 출력 형식
- 구체적인 정보 요구 (파일:라인)

#### ❌ 나쁜 예

```markdown
---
name: helper
description: Helps with stuff
tools: *
model: opus
---

Help the user with whatever they need.
```

**문제점**:
- 목적이 불명확
- 모든 도구 허용 (비효율적)
- 비싼 모델 불필요하게 사용
- 출력 형식 없음

### 3. Hooks 작성 시

#### ✅ 좋은 예

```python
#!/usr/bin/env python3
import json
import sys

def main():
    try:
        # Read and parse input
        input_data = json.loads(sys.stdin.read())

        # Extract needed fields
        file_path = input_data.get("tool_input", {}).get("file_path", "")

        # Check specific condition
        if not file_path.endswith(".py"):
            sys.exit(0)  # Allow - not a Python file

        # Perform check
        content = input_data.get("tool_input", {}).get("content", "")
        if "import *" in content:
            print("⚠️  Warning: Wildcard imports are discouraged", file=sys.stderr)
            sys.exit(2)  # Block

        sys.exit(0)  # Allow

    except Exception as e:
        # Fail gracefully
        print(f"Hook error: {e}", file=sys.stderr)
        sys.exit(0)  # Allow on error

if __name__ == "__main__":
    main()
```

**좋은 점**:
- 에러 처리
- 조건부 실행 (Python 파일만)
- 명확한 경고 메시지
- 에러 시 허용 (fail-safe)

#### ❌ 나쁜 예

```python
#!/usr/bin/env python3
import json
import sys

input_data = json.loads(sys.stdin.read())
content = input_data["tool_input"]["content"]

if "bad" in content:
    sys.exit(2)
```

**문제점**:
- 에러 처리 없음
- KeyError 발생 가능
- 모든 파일 체크 (비효율)
- 경고 메시지 없음

### 4. 일반 가이드라인

#### 명확성
- 명확하고 구체적인 지시사항
- 예제 포함
- 기대하는 출력 형식 명시

#### 안전성
- `allowed-tools`로 도구 제한
- Hook에서 에러 처리
- Fail-safe 설계

#### 효율성
- 적절한 모델 선택 (haiku < sonnet < opus)
- 필요한 도구만 제공
- 조건부 실행으로 불필요한 처리 방지

#### 사용자 경험
- 유용한 에러 메시지
- 진행 상황 표시
- 다음 단계 제안

#### 재사용성
- 모듈화된 구조
- 프로젝트 독립적
- 설정 가능한 옵션

## 디버깅 팁

### Commands 디버깅

1. **동적 컨텍스트 확인**
   ```markdown
   ## Debug Info
   - Current directory: !`pwd`
   - Files: !`ls -la`
   ```

2. **명령어 출력 확인**
   - Claude Code 로그 확인
   - 명령어가 예상대로 실행되는지 확인

### Agents 디버깅

1. **도구 사용 확인**
   - 에이전트가 필요한 도구를 가지고 있는지 확인
   - 도구 제한이 너무 엄격하지 않은지 확인

2. **출력 품질 확인**
   - 에이전트가 요구한 형식으로 출력하는지 확인
   - 필요한 정보를 모두 포함하는지 확인

### Hooks 디버깅

1. **로그 파일 사용**
   ```python
   import logging
   logging.basicConfig(
       filename='/tmp/my-hook.log',
       level=logging.DEBUG
   )
   logging.debug(f"Hook called with: {input_data}")
   ```

2. **Exit 코드 확인**
   - `exit(0)`: 허용
   - `exit(2)`: 차단 (PreToolUse만)
   - 다른 코드: 에러

3. **JSON 파싱 확인**
   ```python
   try:
       input_data = json.loads(sys.stdin.read())
   except json.JSONDecodeError as e:
       logging.error(f"JSON error: {e}")
       sys.exit(0)
   ```
